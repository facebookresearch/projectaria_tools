# Changelog

---
## Version 1.4.0

### Platform Support

- The macOS (Apple Silicon) wheels now require macOS 15 or newer; macOS 14 is no longer supported. Linux wheels are unchanged

### New Features

- **ET ML V2 eye valid scores** are checked on `Gaze Data Class` streams recorded with the `et_ml` flavor and algorithm version `2.0`, in `AriaGen2_Default` and `AriaGen2_CI`. Other eye gaze streams report passing values
- **Phone location**: the Oatmeal phone location stream, a GPS stream with provider `app`, is now checked and reported as `GPS Data Class (phone_location)` instead of being skipped. It has no fixed rate, so it's checked as events: a malformed fix counts as `bad` by the same rules as GPS, a capture timestamp that doesn't move forward counts as `non_monotonic`, and a good fix whose UTC time goes backward counts as `utc_out_of_order_samples`. Records with no fix, a 0 Hz configuration, and a repeated fix stay healthy
- Phone location in recordings made before December 2025, where the phone and the glasses' GPS streams share the flavor `device/oatmeal`, is also checked. It's named by its stream class, so the glasses' GPS keeps its own name and checks. GPS streams with provider `app` from producers other than the Oatmeal recorder are skipped with a warning
- **Light flicker detection** records are now checked as detection events rather than periodic samples. The detector writes a record only when a sensor capture completes, so a stream with few or no records is healthy. A record counts as `bad` when its capture timestamp is negative or a frequency/magnitude pair is malformed: an infinite, negative or NaN magnitude, an infinite or negative frequency, or a NaN frequency with a nonzero magnitude. An unused slot (NaN frequency, zero magnitude) and a zero frequency are valid
- When the recording profile enables `als_flicker_detection`, the light flicker stream must be present, even if it holds no records. Light flicker streams from producers other than the Oatmeal recorder are skipped with a warning
- **Expected failures**: VIO and high-frequency pose results missing while VIO is down for an expected cause (vehicle, high travel speed or dark) are reported as `dropped_during_expected_vio_failure` instead of `dropped`. When GPS before a VIO failure has too few fixes to tell the speed, the fixes during the failure are used too, reported as `gps_speed_during_failure_mps`. An empty PPG stream warns instead of failing when the recording's boot probe found no PPG sensor. Each downgrade is listed under a new `expected_failures` key, and a missing or failed PPG sensor under `device_health_findings`, in every configuration's report
- VIO results missing from a reset, or from the start of the recording, until 1 s after VIO's first valid result are reported as `dropped_during_init` instead of `dropped`, so expected re-initialization gaps no longer count toward the VIO drop ratio. Gaps that began before the reset, and gaps after an initialization longer than 5 s, still count as drops
- When the recording profile enables nullformer audio, its `soc_audio_nullformer` stream must be present

### Configuration Updates

`thresholds_version` moves up on every Gen2 configuration: `AriaGen2_Default` and `AriaGen2_CI` to `thresholds_v1.3`, `AriaGen2_Location` to `thresholds_v1.2`, `AriaGen2_Handtracking` to `thresholds_v2.2`. Gen1 is unchanged.

#### `AriaGen2_Default` and `AriaGen2_CI` configurations:
- Added `valid_score_check.scores_present` (warns when no frame carries a score, as in recordings made before the device published scores), `valid_score_check.ratio_frames_missing_a_score` (fails above 1%), `valid_score_check.out_of_range_scores` (fails any score outside [0, 1]) and `valid_score_check.ratio_flag_score_mismatch` (fails above 1% of scored eyes whose valid flag disagrees with score ≥ 0.7)

#### `AriaGen2_Default` configuration, inherited by `AriaGen2_CI` and `AriaGen2_Location`:
- `GPS Data Class (phone_location)` adds `bad` and `utc_out_of_order_samples` (warn above 0) and `non_monotonic` (fail above 0). It's non-periodic, so the cadence-derived checks don't apply to it
- GPS `bad` now also counts a fix with a negative speed, on both `GPS Data Class` and `GPS Data Class (phone_location)`. A fix whose speed is unknown (NaN) stays healthy

#### `AriaGen2_Default` configuration, for light flicker detection, inherited by `AriaGen2_CI`:
- `Light Flicker Detection Data Class` is now non-periodic, so `total`, `ratio_dropped_over_expected` and the start and end offsets no longer apply to it, nor does `AriaGen2_CI`'s `longest_consecutive_drop`. It keeps `bad` and `non_monotonic`, both failing above 0

#### `AriaGen2_Handtracking` configuration:
- `GPS Data Class (phone_location)` is ignored, as `GPS Data Class` is

### Bug Fixes

- A light flicker stream recorded with `rate_hz=0` is now checked, rather than dropped from the report
- Light flicker magnitudes that are NaN or infinite, and infinite frequencies, now count as `bad`; previously only negative values did

## Version 1.3.2

### Platform Support

- Wheels for Python 3.13 and 3.14, on macOS (Apple Silicon) and Linux (x64). The Linux wheels for 3.13 and 3.14 need glibc 2.28 or newer; 3.10 to 3.12 keep the glibc 2.17 floor

### New Features

- Proximity Sensor Data Class records are now parsed and checked, not only counted. A record with a nonpositive capture timestamp or an unrecognized sensor state counts as `bad`, and timestamps that go backward count as out of order. `invalid` is a legitimate sensor state, reported separately as `invalid_value_samples`
- Proximity streams from producers other than the Oatmeal recorder are skipped with a warning rather than checked

### Configuration Updates

#### `AriaGen2_Default` configuration, inherited by `AriaGen2_Location` and `AriaGen2_CI`:
- GPS `bad` now warns when any GPS record is malformed: a negative capture timestamp, a fix with some position fields missing, a fix with non-finite or out-of-range position or accuracy, or a fix with a UTC time before 2020. Records with no fix at all, which are normal indoors, stay healthy
- Added GPS `utc_non_monotonic`, which warns when a good fix's UTC time doesn't move forward
- GPS `bad_samples_with_valid_fix` is now ignored, since every sample it counts also raises `bad`
- GPS stats add `no_fix_samples`, `inconsistent_fix_samples` and `utc_non_monotonic`

#### `AriaGen2_Default` configuration, for proximity:
- `Proximity Sensor Data Class` adds `bad` (fail above 0) and `ratio_out_of_order_over_total` (warn above 0.001, fail above 0.01)
- `Proximity Sensor Data Class` is now non-periodic, so the cadence-derived checks no longer apply to it

#### `AriaGen2_CI` configuration:
- Inherits the proximity checks above. Its `longest_consecutive_drop` ignore for `Proximity Sensor Data Class` is removed, since a non-periodic stream doesn't receive that check

### Bug Fixes

- A malformed GPS record is counted once in `processed`, rather than twice
- A GPS record with a negative capture timestamp no longer corrupts the stream's drop, timing and monotonic checks

## Version 1.3.1

### New Features

- Added `longest_consecutive_drop` to every periodic stream's stats: the largest run of consecutive missing samples. Reported for all configurations, checked by `AriaGen2_CI`
- Added support for the **SoC audio stream**, reported separately from microphone capture as `Stereo Audio Class (soc_audio)`. It carries samples only while a session is producing audio, so it is now treated as non-periodic and no longer inherits the cadence-derived checks

### Configuration Updates

`thresholds_version` moves up a minor version on every Gen2 configuration: `AriaGen2_Default`, `AriaGen2_Location` and `AriaGen2_CI` to `thresholds_v1.1`, `AriaGen2_Handtracking` to `thresholds_v2.1`. Gen1 is unchanged.

#### All `AriaGen2_*` configurations:
- `duration_overrides`, previously used only by GPS, now covers every check whose value scales with recording length: a `≤ 60s` band relaxes warn 5x (capped at the check's own fail threshold) and fail 2x, so a single dropped frame in a ~30s clip no longer warns. Max, absolute-timing and count checks are unchanged
- `Pose Data Class (vio).reset_frequency_per_min` gets `≤ 30s` and `≤ 60s` bands, so a single reset in a short clip passes while a second still warns
- A `duration_overrides` entry may now set `fail_threshold`, `warn_threshold` or both; one that sets neither is rejected when the configuration loads, rather than passing every value

#### `AriaGen2_CI` configuration:
- Overrides now reach the global `periodic` block, so all periodic streams are tightened at once rather than only the ones named explicitly
- Tightened drop-ratio fail thresholds (short clip / long clip): `periodic` 0.04 / 0.02 → 0.02 / 0.01, `Camera Data (SLAM)` 0.02 / 0.01 → 0.005 / 0.001, `GPS Data Class` 0.10 / 0.02 → 0.02 / 0.01
- Added `longest_consecutive_drop` checks: fail at 1 on `periodic`, at 11 on `IMU Data (SLAM)` (derived from its `longest_imu_skip_us` limit). Ignored on `Pose Data Class (vio)`, `Pose Data Class (vio_high_frequency)`, `EMG Data Class (emg_imu_batch)` and `Proximity Sensor Data Class`, whose sample cadence does not make a consecutive-drop count meaningful

### Bug Fixes

- The threshold reported alongside a result now reflects the duration band that produced the verdict. The console summary and the `fail_threshold` / `warn_threshold` fields in the output JSON previously showed the check's declared value, so a failure could read `0.28 <= 1`

## Version 1.3.0

### New Features

- Added support for the **Light Flicker Detection stream**: the tool now recognizes this stream and reports it in the output JSON as `Light Flicker Detection Data Class`, with a `bad` check for malformed records
- Reworked **Meta Neural Band** health checking to be based on the batch sequence number rather than on timestamp cadence, which is unreliable for the stream's bursty batch timestamps. Under `EMG Data Class (emg_imu_batch)` this adds:
  - `ratio_dropped_batches_over_expected`: batches missing from the sequence, over the number expected across the observed span (fail 50% / warn 10%)
  - `non_monotonic_sequence`: batches whose sequence number goes backwards
  - `zero_channel_count` and `mismatched_channel_count`: batches whose EMG channel count is absent or inconsistent
  - `ratio_dropped_over_expected` is now ignored for this stream, superseded by the sequence-based ratio above
- Added recording-level temperature tracking to camera stats: `min_temperature_c` and `max_temperature_c` report the coldest and hottest frame temperature seen across the whole recording, alongside the existing `temperature_out_of_range` count. Cameras without a temperature probe (for example the eye-tracking cameras) report non-finite values and are skipped

### Configuration Updates

#### `AriaGen2_CI` configuration:
- Tightened IMU drop and timing thresholds, so CI recordings are held to a stricter standard than the general-purpose configurations

### Bug Fixes

- The wheel no longer installs a top-level `_core_pybinds` module. It was built and packaged unintentionally, and because `projectaria-tools` installs a module of the same name, whichever package was installed second silently overwrote the other's copy — leaving `import projectaria_tools` failing with an `ImportError` when this package won. The two packages can now be installed in either order

## Version 1.2.1

### New Features

- Added support for the **Proximity Sensor stream**: the tool now recognizes this stream and reports it in the output JSON
- Added **duration-aware threshold overrides** for numeric checks: thresholds can now declare relaxed values that apply only to short recordings, via a new `duration_overrides` field (see [Configurations and Threshold Checks](./configuration_and_thresholds#1-numeric-checks))
- Added new camera timing check `ratio_large_deviation_over_total`: the percentage of frames whose timing deviates from the expected period by more than a configurable amount

### Configuration Updates

#### `AriaGen2_Default` configuration:
- Added `Proximity Sensor Data Class` checks (only applied to recordings whose firmware emits this stream)
- Relaxed GPS `start_offset_from_file_us` warn threshold from 3,000,000µs to 6,000,000µs
- Added a duration override for GPS `ratio_dropped_over_expected`: recordings ≤ 60s use fail 10% / warn 5% (default remains fail 2% / warn 1%)
- Disabled GPS `percentage_inaccurate_samples` and `percentage_invalid_raw_measurement_samples` (set `ignore: true`) to reduce false warnings on valid-but-inaccurate GNSS fixes

#### `AriaGen2_Location` configuration:
- Camera timing: removed `largest_deviation_from_period_us` fail threshold (kept `warn_threshold` at 250µs)
- Camera timing: added `ratio_large_deviation_over_total` fail threshold at 0.1%, using a 500µs deviation threshold

### Bug Fixes

- Fixed camera large-deviation frame counting so it now matches the periodic stream's behavior
- Lowered the log level of the `calib_json_tag_correct` check from error to warning when an unexpected exception occurs (the check result is still reported in the final summary)

- Increased longest repeating gyro fail threshold from 10 to 15

- Updated Aria Gen1 SLAM camera exposure valid range from `[0.10ms, 48ms]` to `[0.019ms, 14ms]`

### New Features

- Added `streams_match_profile` check to verify expected stream counts match recording profile (Aria Gen2 only)
